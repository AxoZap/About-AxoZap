# Internship tracker

The site at `internships.axozap.com` is protected by the **Internship Tracker** Cloudflare Access application. All browser data requests use the same-origin `/api/internships` Pages Function. That Function forwards the Access JWT to the backend Worker, which verifies the JWT signature, issuer, and application audience before any D1 query or mutation. The public `workers.dev` URL also requires that JWT. `/health` remains public and contains no internship data.

The Worker configuration in `worker/wrangler.jsonc` contains the non-secret Access team domain and application audience. If the Access application is recreated, update its audience in that file before deploying. Do not add an `ADMIN_PASSWORD`: the old optional password path was removed because it allowed writes when the secret was absent.

Deploy the Worker with `cd worker && npm ci --legacy-peer-deps && npm run deploy`. Push the `Internships` changes to the repository's `main` branch to trigger the existing Cloudflare Pages Git deployment. Deploy both parts together: the site now calls `/api/internships`, and the Worker now requires the JWT forwarded by that route.

Cloudflare Access JWT validation: https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/

The small **SQL** button in **Add Application** reveals a SQL editor. Its `/api/sql` endpoint verifies Access and permits only the configured `SQL_OWNER_EMAIL`, from `SQL_ALLOWED_ORIGIN`. Multiple ordinary SQLite statements run together as an atomic batch; query output is capped at 100 displayed rows per statement. Use the D1 console for trigger definitions. Run the local endpoint tests with `cd worker && npm test`.

The tracker has six mutually exclusive main statuses: **Applied, Rejected, Withdrawn, Removed, Bookmarked, Offer**. Applied entries show an additional progress picker: **Application, Assessment, Interview**. Round inputs appear only after choosing Assessment or Interview, including reselecting the current stage, and hide after reload. Numbers are manual; selection never advances a round. Returning to Applied restores the last recorded progress and number. Application cannot be chosen as a later progress stage. The row actions contain Edit and Delete; Delete asks for confirmation. Main status changes replace the separate rejection/withdrawal toggles.

The table defaults to **Applied**. Its status filter offers all six main statuses plus the three progress stages (within Applied). **All Statuses** includes every record. Summary counts always cover the entire tracker. Closed combines Withdrawn and Removed, while the other counts are Applied, Rejected, Bookmarked, and Offer; Total is separated visually. The Closed filter shows both categories. Terms always sort chronologically first; the selected sort field and direction apply within each term, initially Date Applied descending. Reset restores these defaults.

The **Flow diagram** button generates a Sankey diagram from recorded history and offers an SVG download. Select **Overall** or a specific time frame (the application's Season / Term), ordered chronologically. Opening it from a filtered term preselects that term. Diagram scope is independent of the table's status/search/location filters, so outcomes remain visible. Bookmarks are excluded from submitted application flows and counted separately. Applied appears exactly once at the start; skipped stages connect directly. All rejection paths merge at Rejected, withdrawal paths merge at Withdrawn, and Removed paths merge at Removed. Round edits refine the existing visit; explicit changes between rounds create separate visits. Edit an application and expand **Status history** to see persisted snapshots.

### Existing D1 field compatibility

The UI reuses existing D1 fields without rewriting application records or history. `status` retains the progress values `Applied` (Application), `OA` (Assessment), and `Interview Round` (Interview), plus `Offer`, `Bookmarked`, `Removed`, and legacy `Withdrawn`. Removed keeps the previous stage and number in recorded history and restores them when returning to Applied. `interview_round` stores the current Assessment or Interview number. `rejected = 1` means the main status is Rejected. The existing `cancelled = 1` flag now means Withdrawn in the UI, preserving the stage and round. Legacy `status = 'Withdrawn'` rows also appear as Withdrawn. Classification priority is Removed, then Withdrawn (flag or legacy status), then Rejected, then Bookmarked/Offer, then Applied. UI changes clear conflicting flags. Earlier rounds and stages remain in `internship_status_history`, including after switching the main status.

Migrations 0003–0005 add history snapshots, an initial Applied snapshot, and outcome flags. Triggers capture direct SQL/D1 writes atomically too; clients cannot replace history through the API. Existing imported records have baseline snapshots because their earlier intermediate stages were not recorded. Migration **0006_resume_applied.sql** removes the obsolete database restriction on returning to Applied, allowing restoration from a main status such as Offer or a legacy withdrawal. It changes no application/history data or authentication. The UI still prevents selecting Application as a later stage, and the diagram always places Applied only at the start.

Apply pending migrations with `cd worker && npx wrangler d1 migrations apply axozap-internships-db --remote` before deploying the Worker, then push the frontend to `main`. For a fresh database created from `schema.sql`, apply migrations 0003 onward (0001 and 0002 are already represented in the base schema). Run `npm test` (Node 22.6+), `npm run build`, and `cd worker && npm test` for status, sorting, diagram, persistence, and authentication checks.
