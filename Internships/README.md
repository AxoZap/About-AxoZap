# Internship tracker

The site at `internships.axozap.com` is protected by the **Internship Tracker** Cloudflare Access application. All browser data requests use the same-origin `/api/internships` Pages Function. That Function forwards the Access JWT to the backend Worker, which verifies the JWT signature, issuer, and application audience before any D1 query or mutation. The public `workers.dev` URL also requires that JWT. `/health` remains public and contains no internship data.

The Worker configuration in `worker/wrangler.jsonc` contains the non-secret Access team domain and application audience. If the Access application is recreated, update its audience in that file before deploying. Do not add an `ADMIN_PASSWORD`: the old optional password path was removed because it allowed writes when the secret was absent.

Deploy the Worker with `cd worker && npm ci --legacy-peer-deps && npm run deploy`. Push the `Internships` changes to the repository's `main` branch to trigger the existing Cloudflare Pages Git deployment. Deploy both parts together: the site now calls `/api/internships`, and the Worker now requires the JWT forwarded by that route.

Cloudflare Access JWT validation: https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/

The small **SQL** button in **Add Application** reveals a SQL editor. Its `/api/sql` endpoint verifies Access and permits only the configured `SQL_OWNER_EMAIL`, from `SQL_ALLOWED_ORIGIN`. Multiple ordinary SQLite statements run together as an atomic batch; query output is capped at 100 displayed rows per statement. Use the D1 console for trigger definitions. Run the local endpoint tests with `cd worker && npm test`.

The **Flow diagram** button in the stats bar generates a Sankey diagram from recorded status history and offers an SVG download. It includes all applications regardless of table filters and excludes bookmarks. Recorded changes connect directly, including skipped stages, repeated later stages and interview rounds. Applied is always included exactly once at the start; it cannot be selected again after an application progresses. Withdrawals are terminal outcomes. Rejection toggles do not duplicate stage visits; all currently rejected applications join one Rejected endpoint. Edit an application and expand **Status history** to see its saved snapshots.

Migration `0003_status_history.sql` adds a history table and database triggers, so status, interview-round and rejection changes are captured atomically even through SQL or direct D1 access. Clients cannot replace history through the application API. Existing records get a baseline snapshot of their current status at migration time; earlier intermediate stages remain unknown. Migration `0004_applied_first.sql` ensures every application has a fixed Applied starting snapshot, repairs legacy history that started at OA, and rejects moves back to Applied in D1 as well as the API. New applications begin with Applied even when a later current status is selected; bookmarks get this starting snapshot when activated. The API returns the persisted history after writes and reloads.

Apply `cd worker && npx wrangler d1 migrations apply axozap-internships-db --remote` **before deploying the updated Worker**, then push the frontend to `main`. For a fresh database created from `schema.sql`, apply migrations 0003 and 0004 afterward (0001 and 0002 are already represented in the base schema). Run `npm run test:flow` (Node 22.6+) and `cd worker && npm test` for the flow and persistence checks.
